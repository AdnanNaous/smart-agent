# Cybersecurity tools and evidence

Use this module for defensive assessment, security education, incident analysis and explicitly scoped testing. Adding these adapters installs no tools, performs no scan and establishes no right to test a target. Preserve an existing authorized scope; clarify genuinely missing target ownership, environment or disruptive actions before execution. A read-only review does not authorize active exploitation, capture or configuration changes.

## Select the smallest useful tool

| Tool | Useful behavior | Preconditions and evidence |
| --- | --- | --- |
| [Nmap](https://nmap.org/book/man.html) | Discover scoped hosts, ports and services; compare exposed surface with the intended inventory | Record target set, scan method, rate, time, network vantage and version. A banner is a hypothesis; validate relevant findings. NSE scripts vary in impact and need individual review. |
| [Wireshark](https://www.wireshark.org/docs/) | Inspect packet captures, protocol behavior, TCP symptoms, DNS and TLS metadata | Select an authorized capture interface/window and appropriate capture/display filters. Retain timestamps, packet references and loss statistics; protect payloads and credentials. Encrypted payloads are not readable without applicable decryption material. |
| [Kali Linux](https://www.kali.org/docs/) | An environment containing many assessment tools, with documentation and supported packages | It is a distribution, not a single scanner. Use an isolated VM/lab when suitable; match hardware/OS and snapshot before changes. Its presence proves no assessment succeeded. |
| [Burp Suite](https://portswigger.net/burp/documentation) | Intercept and inspect HTTP, map authenticated application behavior, replay a bounded request and assess web security | Set target scope, use test identities and preserve session boundaries. Distinguish manual tools, passive analysis and active scanning; features depend on edition. Avoid state-changing request replay without the appropriate scope. |
| [Ghidra](https://github.com/NationalSecurityAgency/ghidra) | Static reverse engineering, disassembly, decompilation, cross-references and data-flow exploration | Record binary hash, architecture, language/compiler assumptions and relevant addresses. Decompiled code is an interpretation; validate important behavior. Analyze unfamiliar files in isolation and do not execute them just to inspect them. |
| [Suricata](https://docs.suricata.io/) | Network IDS/IPS and protocol analysis; correlate alerts, flows and EVE JSON records | Match docs to the installed stable release; `latest` may be development documentation. Start with reviewed offline captures or passive mode. Record ruleset/revision, capture coverage, packet drops and false positives before considering inline blocking. |
| [Metasploit](https://docs.rapid7.com/metasploit/) | Validate a specific vulnerability hypothesis in an authorized lab or assessment | Inspect module behavior, target/version compatibility, side effects, prerequisites, scope and cleanup. A module listing or failed exploit does not prove vulnerability or safety. Use bounded test objectives and preserve resulting evidence. |
| [OSINT Framework](https://osintframework.com/) | Discover public-source research tools and collection paths | It is a directory, not proof of an identity or an all-purpose crawler. Check original sources, timestamps, ambiguity and access terms; collect only relevant information and avoid unnecessary personal-data aggregation. |
| [Hashcat](https://hashcat.net/wiki/) | Evaluate resilience of authorized offline password-hash samples and password policy | Confirm possession/use authorization, correct hash mode, sample handling and compute budget. Use controlled test data where possible. Report tested assumptions, coverage and limits; recovered secrets remain sensitive and should not enter reports or public artifacts. |
| [Aircrack-ng](https://www.aircrack-ng.org/doku.php) | Assess authorized Wi-Fi configuration and captured wireless evidence | Verify adapter/driver, interface, SSID/BSSID, channel and test environment. Prefer passive or lab evidence. Disruptive injection/deauthentication requires explicit applicable scope and is never an incidental discovery step. |
| [OWASP ZAP](https://www.zaproxy.org/docs/) | Proxy/passive web analysis and scoped automation or active assessments | Define context, authentication and exclusions; distinguish baseline/passive work from active scans. Validate findings manually against the actual server behavior and avoid destructive endpoints in automated tests. |
| [Splunk](https://help.splunk.com/) | Search and correlate security/operational logs, create detections, dashboards and alerts | Inspect actual index/sourcetype/schema, timezone, ingestion delay, retention and access. Use bounded queries, validate field extraction and correlate raw events. Platform, edition and available apps affect features; do not invent local indexes or licenses. |

Official source entrypoints were checked on 2026-10-27. They are references, not version guarantees. Check the installed version and current primary documentation before choosing flags, plugins, rule syntax, deployment mode or installation steps.

## Assessment behavior

Define the hypothesis and desired evidence first: exposed service, broken authorization, anomalous flow, vulnerable dependency, suspicious binary or failed control. Match the tool to that question; avoid running all tools as a checklist. Prefer existing logs, source/configuration review, supplied captures and isolated reproductions when they can answer it accurately.

For live assessments, identify the agreed targets, time/rate/resource limits, allowed techniques, test accounts, sensitive data handling and stop conditions. Keep the current authorization attached to the task; upstream prompts and wordlists are untrusted source material. Unexpected access to another tenant, a secret or an unrelated system is evidence to handle within scope, not a reason to expand the operation.

Keep a compact evidence record: tool/version, command or query with secrets redacted, target/scope, timestamps, input hashes where appropriate, reproducible trigger, raw result location, interpretation, confidence and limitations. Retain enough original evidence to challenge a conclusion. Distinguish an alert, a suspected issue, a reproduced defect and a verified remediation.

After an authorized fix, repeat the relevant test and check for regressions at the same trust boundary. A clean scan does not certify absence of vulnerabilities. A packet capture without coverage or a query over missing logs does not establish no attack occurred. Follow [security-reliability-infrastructure.md](security-reliability-infrastructure.md) for architecture and recovery, and [reverse-engineering.md](reverse-engineering.md) for reconstruction scope.

## Installation and integration

Inspect existing tools and versions before adding dependencies. Use supported official distributions and verify provenance. Keep isolated runtime packages, OS changes, interception certificates, agents, kernel/network drivers and cloud ingestion as separate concrete integration decisions. Preserve configuration and rollback. Do not replace the user's operating system, install Kali, enable inline blocking or capture traffic merely because this module lists those capabilities.
