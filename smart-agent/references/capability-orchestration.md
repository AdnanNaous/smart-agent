# Capability-first orchestration

## Discover enough to act

Use live tool schemas, available environments, model/control descriptions, installed domain skills, workspace evidence, and user preferences. Revisit discovery when the task changes, the catalog changes, or an attempted operation reveals a mismatch. Avoid enumerating every plugin or researching a leaderboard each turn.

Treat capability examples as open-ended. A future mechanism may combine research, engineering, and operation more effectively than separate tools. Prefer it when its actual affordances fit the requested result. Its existence does not by itself grant authority to use connected accounts or modify external state.

Distinguish tool availability, account access, authorization, and confirmed execution. Public model documentation does not establish session entitlement or supported spawn parameters. An unknown model ID can be valid if the runtime exposes it; judge it from available capability information and evidence rather than its name.

## Compose work using native judgment

Use the current model and a coordination structure justified by the work. A simple stable answer may need no tools. A current comparison may need source retrieval and synthesis. A bug may need code/log inspection, implementation, and regression verification. A large product may combine research, architecture, execution, creative work, and QA. These are examples, not prescribed pipelines.

Let the model choose decomposition, research depth, architecture, debugging strategy, and verification from the task. Use plans to manage real uncertainty or dependencies, not to satisfy the skill. Prefer relevant purpose-built capabilities while honoring the user's explicit tools and constraints.

## Optional model and effort selection

For this installation's Terra 6.1 candidate and the requested Codex Auto Model Router integration, read [model-routing.md](model-routing.md). Its dated catalog is advisory; verify exact model IDs and effort support on the target tool. Upstream routing defaults do not override the current runtime or explicit user choices.

Use supported selection controls only when a bounded task has a meaningful advantage from another model or specialist context. Otherwise keep the current model. Respect a user's selected main model and effort; a name in conversation is a preference, not proof of the executing model. Label unknown or inherited settings honestly.

Consider capability, context, specialization, latency, reliable cost/quota information, verification difficulty, rework, and handoff overhead together. Model capability and reasoning effort are different dimensions; effort labels are not comparable units of intelligence or cost across models. No fixed low-to-high ladder, effort ceiling, family hierarchy, or generation mapping is required.

Explicit model/effort pairs are useful only when intentionally selecting supported overrides. Use inheritance when appropriate or requested. Follow the live schema for model IDs, effort values, history forks, and limits instead of copying a frozen invocation example.

Economy favors focused work, fewer handoffs, and sufficient checks. Quality favors useful judgment and verification, not maximum agents or maximum deliberation everywhere. Do not claim quota savings from model labels. A hard spend cap requires measurable and enforceable controls; disclose when those are unavailable.

## Diagnose before changing the route

Obtain missing context or evidence before blaming model capability. Revise a sound approach that missed conditions; deepen reasoning when useful. Consider a different model or independent judgment for persistent conceptual errors or difficult synthesis. Address credentials, permissions, dependencies, network, and hardware issues as actual blockers.

Skip predictably inadequate attempts when difficulty is clear. Retry with new evidence or a changed hypothesis rather than merely another agent. Use no universal escalation count; respect explicit budgets, runtime limits, and whether the next attempt can materially improve the result.

## Adapt across environments

Use capabilities where actually exposed, whether in a chat, coding runtime, cloud workspace, app integration, or future environment. Missing delegation does not prevent direct work; missing browser access may still permit source or code checks. State the effect of missing capabilities on verification.

A phone/chat conversation can communicate goals and review outputs while available tools do execution elsewhere. Do not claim automatic transfer to Work, Codex, another chat, a local computer, or a background worker unless a real supported mechanism performs it. If transfer is unavailable, complete feasible work and provide a compact handoff for the remaining environment-dependent action.

## Evolve working knowledge

Reconsider an established method when new capabilities, changed interfaces, current primary sources, or observed failures reveal a better option. A reference website, benchmark, package, production tool, or agent pattern can be replaced when evidence supports the change. Explore useful alternatives within the authorized environment; use failures to revise the hypothesis and inspect the result rather than simply repeating the same attempt.

Preserve transferable findings where the runtime actually supports persistence. Record the relevant task, system/version or conditions, observation, evidence, and implication only as needed for reuse. Keep project facts in project state; put durable cross-task lessons in the skill when maintenance is authorized. Remove obsolete guidance and unnecessary constraints instead of accumulating every experiment. Revalidate affected examples and behavior after a meaningful instruction change, retaining enough history to reverse a regression. This is evidence-driven maintenance, not a promise of autonomous training or unattended execution.
